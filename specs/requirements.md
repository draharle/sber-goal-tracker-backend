# Требования: сервис модуля ККД (backend)

Спецификация решения. Источник — тестовое задание «Backend-разработчик (Java)»
и эталонный mock API модуля ККД (формы ответов, коды ошибок, термины).

## Что делает решение

Сервис проверяет качество данных по целям и ключевым результатам (КР), хранит результаты проверок
(«прогонов») в PostgreSQL и отдаёт их фронтенду через REST API: метрики подразделения с учётом дочерних,
найденные проблемы и дельту с прошлым прогоном. Фронтенд ничего не досчитывает сам.

## Термины

- **Активная цель** — цель в статусе `active` (остальные: `draft`, `closed`, `cancelled`). Правила проверяют только активные цели и их КР.
- **Каскад** — цели связаны в дерево: блок → департамент (hq) → подразделение (unit) → сотрудник (employee).
- **Прогон** — одна проверка всех данных на дату снимка. Статусы: `running`, `completed`, `failed`.
- **Проблема** — нарушение правила на конкретном объекте (цели или КР).
- **Отпечаток (fingerprint)** — `КОД_ПРАВИЛА:id_объекта`. Проблемы двух прогонов — «одна и та же», если отпечатки совпадают.

## Правила (4 из 6 предложенных)

| Код | Важность | Объект | Когда срабатывает |
|---|---|---|---|
| `GOAL_NO_KR` | critical | цель | у активной цели нет ни одного КР |
| `KR_WEIGHTS_SUM` | major | цель | у активной цели есть КР, но сумма их весов ≠ 100 |
| `CASCADE_NO_PARENT` | major | цель | цель уровня hq / unit / employee без родителя (или родитель не найден) |
| `KR_STALE_PROGRESS` | minor | КР | дата снимка − дата обновления факта > 45 дней |

## Метрики (по подразделению вместе со всеми дочерними)

| Ключ | Название | Ед. | Лучше, когда | Формула |
|---|---|---|---|---|
| `clean_goals_share` | Доля корректных целей | % | выше | активные цели без проблем ÷ все активные × 100 |
| `cascade_coverage` | Покрытие каскадом | % | выше | активные цели ниже блока без `CASCADE_NO_PARENT` ÷ все такие × 100 |
| `issues_total` | Найдено проблем | шт. | ниже | число проблем по целям подразделения |

Доли округляются до 0,1. Нет активных целей — все три метрики `null`.

## Критерии приёмки

Рядом — тест, который это проверяет.

1. **Схема БД**: подразделения с иерархией, сотрудники, цели (ответственный, родитель, уровень, статус, срок), КР (цель, факт, вес, дата обновления факта); справочник правил, прогоны, проблемы, метрики прогона. — `LiquibaseRollbackTest`
2. **Миграции**: накат → полный откат → повторный накат проходят без ошибок, у каждого changeset есть rollback, включая стартовые данные. — `LiquibaseRollbackTest`
3. **Стартовые данные**: 26 целей (23 активные) в департаменте и двух управлениях + цель блока; есть нарушения каждого из 4 правил; два успешных прогона (RUN-001, RUN-003) и упавший между ними (RUN-002); между успешными есть new, persisting и resolved. — `KkdApiTest.runs`, `summaryLatestForRoot`
4. **Правила на граничных данных**: веса 99 / 100 / 101; пустой список КР; 45 и 46 дней; неактивные цели не проверяются; цель блока без родителя — норма. — `KrWeightsSumRuleTest`, `GoalNoKrRuleTest`, `KrStaleProgressRuleTest`, `CascadeNoParentRuleTest`
5. **Движок отделён** от API и БД: на входе снимок данных, на выходе список проблем; тестируется без Spring и без БД. — тесты пакета `engine`
6. **Метрики с учётом дочерних**: департамент считается вместе с управлениями; подразделение без активных целей → `null`, а не 0. — `MetricsCalculatorTest`, `KkdApiTest.summaryCascadeAndEmptyUnit`
7. **Дельта**: у первого прогона `previous`, `delta` и счётчики new / persisting / resolved равны `null`; та же проблема = то же правило + тот же объект; сравнение — с предыдущим **успешным** прогоном, упавший пропускается. — `DeltaCalculatorTest`, `KkdApiTest.summaryFirstRun`, `KkdApiTest.runs`
8. **trend** учитывает `higher_is_better`: рост «Найдено проблем» — `worse`, рост доли — `better`, дельта 0 — `same`. — `DeltaCalculatorTest.trendRespectsHigherIsBetter`
9. **GET /api/runs**: статус, дата снимка, с каким прогоном сравнивается, число проблем (у упавшего — `null`). — `KkdApiTest.runs`
10. **GET /api/kkd/summary?run_id=&unit_id=**: формат как во фрагменте задания + `higher_is_better`; `run_id` по умолчанию `latest` (последний успешный), `unit_id` — корень оргструктуры. — `KkdApiTest`
11. **GET /api/kkd/issues**: фильтры `unit_id` (с дочерними), `rule_code`, `severity` (через запятую), пагинация `limit` (1–200, по умолчанию 20), `offset` (≥ 0), `total`. — `KkdApiTest.issues`
12. **Ошибки** в едином формате `{"error": {"code", "message"}}`: неизвестный прогон / подразделение → 404 `RUN_NOT_FOUND` / `UNIT_NOT_FOUND`; кривые параметры (формат `run_id` / `unit_id`, `limit` вне диапазона, `offset` < 0, нечисловой `limit`, неизвестные важность или правило) → 422 `INVALID_PARAM`; упавший прогон → 409 `RUN_FAILED`. — `KkdApiTest.errors`
13. **Запуск одной командой** `docker compose up`: PostgreSQL 16, миграции и демо-данные при старте сервиса, первый прогон движком. Конфигурация — через переменные окружения (`.env.example`).
14. Дополнительно: **POST /api/runs** — внеплановый прогон; на неизменных данных все проблемы `persisting`. — `RunExecutionTest`

## Вне рамок

Остальные правила эталона (`GOAL_NO_OWNER`, `KR_NO_TARGET`, `CASCADE_WRONG_LEVEL` и др.), карточка проблемы,
выгрузка CSV, расписание прогонов (cron), авторизация. Как добавить правило — `design.md`, «Расширение».
